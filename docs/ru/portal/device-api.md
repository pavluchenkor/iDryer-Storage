# Что должен делать портал или локальное приложение

Этот документ описывает продуктовый контракт `Storage Link` с точки зрения UI/backend.
Не библиотеку и не общий MQTT-контракт платформы, а именно то, что имеет смысл для текущего репозитория.

## Product goals

Портал или приложение должны использовать устройство для двух сценариев:

1. подсветить нужную катушку;
2. показать климат внутри зоны хранения, если на плате есть SHT31.

## Что нужно показать в UI

### Карточка устройства

- `deviceType = "storage_link"`
- `hardwareVersion`
- `firmwareVersion`
- online/offline состояние по стандартной cloud-модели

### Конфиг ленты

Нужно уметь читать и показывать:

- количество светодиодов;
- лимит тока БП;
- тип ленты;
- порядок цветов;
- язык.

Источник данных: `config`.

### Кнопка или сценарий "подсветить катушку"

UI не должен посылать абстрактную команду "highlight spool 123".
Прошивка не знает про ID катушек.

Вместо этого внешний слой обязан сам вычислить:

- какой физический индекс на ленте соответствует нужной катушке;
- каким цветом её подсвечивать;
- сколько держать подсветку.

После этого отправляется `commands/invoke` с `action = "led.pulse"`.

## Что нужно читать из телеметрии

Если приходит:

```json
{
  "units": [
    {
      "unitId": "U1",
      "temperature": 23.5,
      "humidity": 47.2
    }
  ]
}
```

в UI есть смысл показывать:

- температуру;
- влажность;
- время последнего обновления.

Если `telemetry` нет, надо считать возможными три варианта:

- устройство offline;
- датчик не установлен;
- датчик установлен, но не найден на старте.

То есть отсутствие температуры/влажности нельзя автоматически трактовать как ошибку продукта.

## Когда использовать MQTT, а когда local access

### MQTT

Подходит для облачного портала и штатного backend flow:

- topic `idryer/<serial>/commands/invoke`
- topic `idryer/<serial>/commands/set`
- topic `idryer/<serial>/commands/get_config`
- topic `idryer/<serial>/telemetry`
- topic `idryer/<serial>/info`

### Local Access

Подходит для LAN-only приложения рядом с устройством:

- авторизация device token;
- JSON envelope вида `{"type":"command","command":"invoke","data":{...}}`;
- JSON envelope вида `{"type":"command","command":"set","data":{...}}`;
- JSON envelope вида `{"type":"command","command":"get_config","data":{}}`;
- чтение ответов `{"type":"config","data":...}` и `{"type":"telemetry","data":...}` по WebSocket.

Важно не смешивать transport model:

- MQTT здесь адресуется topic-ами;
- Local Access не использует topic path и работает только через JSON WebSocket envelope.

## Что не надо проектировать в UI под этот продукт

На текущем состоянии репозитория `Storage Link` не требует экранов и backend flows для:

- ручного нагрева;
- профилей сушки;
- Moonraker;
- Bambu;
- Home Assistant;
- UART-конфигурации сушилки;
- `integrations/status`.

Если такие сущности есть в другом продукте платформы, это не делает их частью данного репозитория.
