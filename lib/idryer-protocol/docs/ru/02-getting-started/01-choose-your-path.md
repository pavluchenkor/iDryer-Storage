# Выбор траектории

Библиотека и документация покрывают три типовые задачи. Выберите свою — получите ссылку на квикстарт, который ведёт от «у меня чистая IDE» до «вижу в портале iDryer свою телеметрию».

!!! note "Перед началом"
    Прочитайте [../01-overview/](../01-overview/). Без общего представления о трёх узлах (MCU/LINK/Cloud) квикстарт пойдёт тяжелее.

## Траектория 1: «Свой контроллер» (MCU)

**Вы делаете:**

- Свою плату с микроконтроллером (STM32, RP2040, AVR, любой Arduino-совместимый).
- Свою прошивку для этой платы: датчики, PID, экран, меню.
- Используете **готовый** модуль LINK (референсный ESP32-модуль iDryer) для выхода в облако.

**Вы используете из библиотеки:** только UART-раздел — структуры кадров, CRC16. Всё это header-only, без рантайма.

**Квикстарт:** [02-quickstart-controller.md](02-quickstart-controller.md).

Квикстарт показывает, как **без PlatformIO и без зависимостей** собрать кадр `Hello`, посчитать CRC, отправить по UART и принять `HelloAck`. После этого вы понимаете устройство протокола «изнутри» и легко переносите код на любую платформу.

## Траектория 2: «Свой сетевой модуль» (LINK)

**Вы делаете:**

- Свою плату с ESP32 (или совместимым модулем с WiFi).
- Свою прошивку: подключение к облаку, мост UART ↔ MQTT.
- Работаете со сторонним MCU (чужой сушилки или вашего собственного).

**Вы используете из библиотеки:** всё — UART, MQTT, HTTP, парсер команд, автомат состояний облака.

**Квикстарт:** [03-quickstart-bridge.md](03-quickstart-bridge.md).

Квикстарт проводит через сборку в PlatformIO, подключение `idryer-protocol` как `lib_deps`, первый запуск с проверкой Hello от MCU, первый MQTT-трафик.

## Траектория 3: «Один ESP32 за всё» (standalone)

**Вы делаете:**

- Устройство на одном ESP32, где тот же чип управляет железом и ходит в облако.
- Нет отдельного MCU, нет UART между платами.
- Типичный случай: iHeater, модуль телеметрии, простые продукты.

**Вы используете из библиотеки:** MQTT, HTTP, парсер команд, автомат состояний. UART-раздел не нужен — структуры `CommandPayload`, `ProfilePayload` применяются прямо в коде через свою реализацию `ICommandSink`.

**Квикстарт:** [04-quickstart-standalone.md](04-quickstart-standalone.md).

## Матрица «что использовать»

| Компонент библиотеки | MCU | LINK | Standalone |
|----------------------|-----|------|------------|
| UART: структуры payload (`*.h`) | ✅ основное | ✅ | ⚠️ только типы (`CommandPayload` и т.п.) |
| UART: `UartBridge` (рантайм) | опционально | ✅ основное | ❌ не нужен |
| UART: `calculateCrc()` | ✅ | ✅ | ❌ |
| MQTT: `MqttClient` | ❌ | ✅ | ✅ |
| HTTP: `HttpApi` | ❌ | ✅ | ✅ |
| `CommandHandler` | ❌ | ✅ | ✅ |
| `ICommandSink` — `UartCommandSink` | — | ✅ готовый | ❌ пишется свой |
| `CloudStateMachine` | ❌ | ✅ | ✅ |
| `TelemetryPublisher` | ❌ | ✅ | ✅ |

## Если вы не уверены

1. Есть ли у вас отдельная плата с WiFi? Если да — вам нужен LINK, ваш основной код в MCU → **траектория 1**.
2. Планируете делать свой WiFi-модуль? → **траектория 2**.
3. Хотите уместить всё в один ESP32? → **траектория 3**.

## После того как квикстарт заработал — привязка к аккаунту

Чтобы устройство появилось в приложении пользователя (и получило возможность принимать команды с портала), его нужно **привязать к аккаунту** — процесс claim.

Три способа привязать:

- **Через экран устройства** — штатный для iDryer с UI.
- **Через веб-инсталлер** — штатный для безэкранных устройств.
- **Через Serial Monitor** — dev-тест, когда нет ни экрана, ни инсталлера под ваш тип устройства (актуально для разработчиков новых продуктов).

Подробно все три — [05-dev-claim.md](05-dev-claim.md).
