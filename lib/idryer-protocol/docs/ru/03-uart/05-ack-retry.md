# ACK, retry, фрагментация

Надёжная доставка в UART-протоколе iDryer строится на трёх механизмах:

1. **ACK** — подтверждение доставки отдельным кадром.
2. **Retry** — повторная отправка при таймауте.
3. **Фрагментация** — разбиение больших payload на чанки.

Все три обслуживаются классом `DryerUart::UartBridge`. Если вы пишете свой парсер вручную — здесь описаны все правила, которые нужно соблюсти.

---

## ACK — подтверждение кадра

### Когда нужен

ACK требуется, если отправитель поставил в заголовке флаг `FLAG_ACK_REQUIRED = 0x01`. Без этого флага кадр считается fire-and-forget: доставлено — хорошо, нет — никто не узнает.

### Для каких типов сообщений по умолчанию требуется ACK

Решение «ставить ли флаг» принимает **отправитель**. В референсной прошивке:

| Тип | ACK по умолчанию |
|-----|------------------|
| `Telemetry` (`0x10`) | опционально (часто без — данные следующие придут) |
| `Weights` (`0x12`) | опционально |
| `Status` (`0x13`) | опционально |
| `Rfid` (`0x14`) | опционально |
| `Command` (`0x20`) | **по умолчанию да** (`sendCommand` в API ставит `ackRequired = true`) |
| `ConfigPush` (`0x30`) | **по умолчанию да** |
| `ClaimStart` (`0x70`) | **по умолчанию да** |
| `Hello` / `HelloAck` | нет (handshake без ACK) |
| `Heartbeat` | нет |
| `Error` | нет |
| `Log` | нет |

### Формат ACK-кадра

Отдельный кадр с соответствующим типом ACK:

| Исходный тип | ACK-тип | Код |
|--------------|---------|-----|
| `Telemetry` | `TelemetryAck` | `0x11` |
| `Command` | `CommandAck` | `0x21` |
| `ConfigPush` | `ConfigAck` | `0x31` |

Все три используют одинаковую структуру `AckPayload` (2 байта): `ackSequence` + `status` (ErrorCode). В **заголовке** ACK-кадра поле `sequence` также равно номеру подтверждаемого кадра (не своему) — это упрощает матчинг.

Для остальных типов с `FLAG_ACK_REQUIRED` отдельного ACK-типа нет; отвечает `Error`-кадром при проблеме или ничего — при успехе (что эквивалентно `Timeout` на стороне отправителя).

### Пример ACK

Подтверждение `Command` c SEQ=7, статус OK:

```
[Заголовок]
  AA       SOF
  01       VER
  02       FLAGS = FLAG_IS_ACK
  21       KIND = CommandAck
  07       SEQ = 7 (номер исходного Command)
  02       LEN = 2

[Payload — AckPayload]
  07       ackSequence = 7
  00       status = None (OK)

[CRC]
  XX XX    CRC16 LE
```

## Retry — повторная отправка

### Параметры

Заданы в `uart_protocol.h`:

| Константа | Значение | Назначение |
|-----------|----------|------------|
| `COMMAND_REPLY_TIMEOUT_MS` | 700 мс | Таймаут ожидания ACK |
| `MAX_RETRIES` | 3 | Максимум повторов |

### Алгоритм

1. Отправляем кадр с `FLAG_ACK_REQUIRED`.
2. Запоминаем кадр в «pending» и засекаем время.
3. Параллельно ждём любой входящий кадр.
4. Через 700 мс после отправки, если ACK не пришёл и `retries < 3` — повторяем отправку **того же кадра с тем же SEQ** и увеличиваем счётчик.
5. После третьего таймаута — отдаём `Error{Timeout}` в `errorHandler_` и очищаем pending.

### Если приходит правильный ACK

- Матчинг по `ackSequence` в payload или по `sequence` в заголовке (должны совпадать).
- Если найден pending с этим SEQ — очистить, retry-счётчик сбросить.
- Если `status != None` — поднять ошибку в `errorHandler_`, pending очистить.

### Что делать приложению

- Для некритичных потоков (Telemetry, Weights) — ACK можно не ставить.
- Для критичных команд (`Command`, `ConfigPush`) — ACK обязателен. Если он не пришёл, устройство, вероятно, в оффлайне.

## Фрагментация: ConfigPush

JSON-конфиг меню размером до ~3 КБ не помещается в один кадр (максимум 200 байт). Разбивается на чанки через `ConfigChunkPayload`.

### Структура `ConfigChunkPayload`

См. [04-binary-structures.md](04-binary-structures.md#configchunkpayload-0x30--до-200-байт):

```
┌─────────────────────────────┐
│ transferId   (uint16 LE, 2) │  ID передачи
│ totalSize    (uint16 LE, 2) │  Полный размер JSON (только при chunkIndex == 0)
│ chunkIndex   (uint16 LE, 2) │  0, 1, 2, ...
│ data[0..193]                │  Фрагмент JSON (≤194 байт)
└─────────────────────────────┘
```

### Флаги фрагментации

| Ситуация | Флаги в заголовке кадра |
|----------|--------------------------|
| JSON ≤ 194 байта, один кадр | `FLAG_LAST_FRAGMENT` |
| Первый фрагмент из нескольких | `FLAG_FRAGMENTED` |
| Промежуточный фрагмент | `FLAG_FRAGMENTED` |
| Последний фрагмент | `FLAG_LAST_FRAGMENT` |

Плюс обычный `FLAG_ACK_REQUIRED` — получатель подтверждает каждый фрагмент **отдельным** `ConfigAck`.

### Протокол сборки на приёмной стороне

1. Приняли кадр с `FLAG_FRAGMENTED` или `FLAG_LAST_FRAGMENT` — это фрагмент конфига.
2. Если `chunkIndex == 0`:
   - Запомнить `transferId` и `totalSize`.
   - Инициализировать буфер размером `totalSize`.
3. Скопировать `data` в буфер по смещению `chunkIndex * CONFIG_CHUNK_DATA_SIZE` (194 байта).
4. Отправить `ConfigAck` с номером SEQ исходного кадра.
5. Если `FLAG_LAST_FRAGMENT` — значит сборка закончена, парсить JSON из буфера.
6. Если приходит фрагмент с другим `transferId` до завершения — текущая передача отбрасывается.

### Ограничения

- `CONFIG_CHUNK_DATA_SIZE = 194` байта на фрагмент.
- В коде `CommandHandler` фрагментация **исходящих** `ConfigPush` (от LINK → MCU при команде `set`/`invoke` с большим JSON) в референсной прошивке не реализована — для малых `set`/`invoke` помещается в один кадр. Это [известное ограничение](../03-uart/03-message-types.md).

## Фрагментация: RfidReadData / RfidWriteData

Другой формат фрагментации, под бинарные данные метки.

- Каждый фрагмент — полный `RfidDataPayload` (199 байт), содержит `readerId`, `unitId`, `tag` (для валидации) и 163 байта данных.
- Количество фрагментов **переменное** — `ceil(readSize / 163)`, зависит от размера user-memory чипа (144–888 Б).
- Флаги `FLAG_FRAGMENTED` / `FLAG_LAST_FRAGMENT` — как у `ConfigPush`. Сборка по `FLAG_LAST_FRAGMENT`, не по счётчику.

**Запись (`RfidWriteData`, 0x1B)** использует **stop-and-wait ACK flow control**: каждый фрагмент идёт с `FLAG_ACK_REQUIRED`, передатчик (LINK) не шлёт следующий до получения `CommandAck`. Причина — приёмник (RP2040) параллельно обслуживает PID/HX711/PN5180, и без pacing hardware-FIFO UART (32 Б) переполняется. Подход основан на XMODEM stop-and-wait и CAN-TP (ISO 15765-2) с STmin. См. [../07-features/01-rfid.md](../07-features/01-rfid.md).

## Идемпотентность и дедупликация

Retry отправителя означает: **один и тот же кадр с тем же SEQ может прийти получателю дважды** (если первый ACK потерялся). Это особенность любого stop-and-wait протокола.

**Референсный `UartBridge` не ведёт дедупликацию по SEQ.** Если получатель обработал запрос, отправил ACK, но ACK потерялся — повтор придёт снова и будет обработан ещё раз. Для идемпотентных операций это безвредно:

- `Telemetry`, `Weights`, `Status`, `Heartbeat`, `Rfid` — перезапись текущих данных, повтор не навредит.
- `Error`, `Log` — диагностика, повтор просто удвоит запись, но не нарушит логику.

Для **неидемпотентных команд** (`Command` c `Start`, `Stop`, `ClearErrors`) приложение должно либо:

1. Принять, что повторная команда безвредна (Start идемпотентен — запуск уже запущенного не ломает логику).
2. Либо самостоятельно запоминать последний обработанный SEQ на приёмной стороне и при повторе игнорировать.

В большинстве сценариев iDryer это не проблема: команды от облака идут редко и вручную, так что двойное Start-событие замечается на уровне UI. Но если вы делаете критичную логику (например, запуск нагревателя до заданного времени) — добавьте проверку `lastHandledSeq == seq`.

## Межбайтовый таймаут парсера

В референсной `UartBridge` сброс парсера выполняется **только при ошибке** (`CrcMismatch`, `InvalidPayload`, `UnknownMessage`). Нет сброса по длительному перерыву в потоке байт. Это значит: если отправитель оборвался в середине кадра, парсер останется в состоянии `Header`/`Payload`/`Crc`, пока не получит достаточное число «продолжающих» байт — которые могут оказаться уже из следующего кадра.

Если вы пишете свой парсер — **добавьте** сброс в `WaitSof` при отсутствии байт более ~50 мс после начала кадра. Это защищает от «застревания» в середине.

## Выравнивание и поля `_pad`

Все `_pad*` поля в структурах (`HelloPayload._pad1`, `StatusEntry._pad`, `RfidPayload._pad`, …) — байты выравнивания. **Отправитель обязан заполнять их нулями.** Это гарантирует:

- CRC считается детерминированно (мусор из стека не попадёт в расчёт);
- приёмник может использовать эти поля в будущем без ломания обратной совместимости.

В библиотечных структурах при `= {}` инициализации `_pad` автоматически нулевой. Если собираете кадр руками — проверьте.

## Правила для самописного парсера

Если вы пишете не через `UartBridge`, соблюдайте:

1. **SEQ** инкрементировать при каждом отправленном кадре, включая ACK, Heartbeat, Error.
2. **FLAG_IS_ACK** — для ACK-кадра. Получатель по нему различает «новый кадр» и «подтверждение моего предыдущего».
3. **В ACK-кадре `sequence` в заголовке** = номер подтверждаемого кадра, **а не своего следующего**.
4. **ACK отправлять как можно быстрее**, не ждать конца обработки payload. Сначала ACK, потом обработка.
5. **Pending queue** — только один pending-кадр одновременно. Если отправили с `ACK_REQUIRED` и ждёте ACK, не слать новый ACK-требующий до получения первого. Не ACK-требующие (Heartbeat, Telemetry без ACK) — можно.
6. **Таймаут между байтами** — добавьте сброс парсера, если разрыв больше 50 мс в середине кадра.
7. **При `payloadLength > 200`** — немедленно отбросить кадр и отправить `Error{InvalidPayload}`.
