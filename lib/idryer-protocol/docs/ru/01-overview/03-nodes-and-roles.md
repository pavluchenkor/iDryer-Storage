# Узлы и их роли

Детальная раскладка: **что делает каждый узел, что у него на входе и на выходе, чем он владеет**. После прочтения вы будете чётко понимать, за что в системе отвечает ваш код, а за что — библиотека и облако.

!!! note "Термины"
    Все термины — в [04-glossary.md](04-glossary.md).

## MCU (Controller)

### Кто это

Микроконтроллер внутри сушилки. В референсной прошивке iDryer — RP2040. Но библиотека **не привязана** к конкретному чипу: UART-раздел работает на любом Arduino-совместимом железе (STM32, AVR, ESP32-C3 и т.д.).

### Задача

Управлять железом сушилки и держать локальный UX.

### Обязанности

- Считывать датчики температуры и влажности.
- Регулировать нагреватель (PID).
- Вести сессию сушки (режимы Drying / Storage / Profile / Fault / Idle).
- Считывать RFID-метки и тензодатчики (если есть).
- Показывать меню и текущее состояние на экране.
- Хранить пользовательские настройки в EEPROM.
- Инициировать привязку устройства по действию пользователя (кнопка «начать привязку»).

### Что MCU получает из библиотеки

Структуры UART-кадров и их определения (`idryer_protocol.h`). Это **header-only** раздел — никакого рантайма. Вы просто включаете `idryer_protocol.h` в проект и получаете готовые `struct` и `enum` с `#pragma pack(1)` и `static_assert` на размеры.

### Что MCU должен уметь

Минимум:

- Отправить `Hello` при старте, приняв `HelloAck`.
- Периодически отправлять `Telemetry`, `Heartbeat`.
- Принимать `Command` и отвечать `CommandAck`.
- Отвечать `HelloAck`-образом на триггер от LINK (`Role = HelloRequest`).

Опционально:

- `Weights`, `Rfid` — если есть соответствующее железо.
- `Status` — если хотите, чтобы облако видело режим работы и таймеры.
- `ConfigPush` — remote config меню.
- `ClaimStart` — привязка устройства.
- `Log` — структурированные события.
- `WsEnable` — локальный WebSocket-доступ без облака.

## LINK (Network module)

### Кто это

Сетевой модуль на ESP32. На нём работает библиотека `idryer-protocol`. В референсном продукте iDryer это отдельная плата, общающаяся с MCU по UART.

### Задача

Связать MCU с облаком iDryer и сделать эту связь надёжной.

### Обязанности

**UART-мост:**

- Принимать кадры от MCU, валидировать CRC, отвечать ACK при необходимости.
- Разбирать кадры и вызывать колбэки прикладного кода.
- Отправлять кадры в MCU.

**WiFi:**

- Подключаться к точке доступа (SSID/пароль либо из прошивки, либо через provision).
- Отслеживать потерю связи, переподключаться.

**HTTP (первичная привязка):**

- `POST /devices/provision` → получение `deviceToken`.
- `POST /devices/register` → получение PIN для пользователя.
- `GET /devices/check-claim/:token` → ожидание claim.

**MQTT:**

- Подключение к брокеру с `serialNumber` как username, `deviceToken` как password.
- Публикация телеметрии, статуса, весов, RFID, конфига.
- Подписка на `idryer/<serial>/commands/#`.
- Обработка входящих команд и преобразование их в UART-кадры.

**Claiming state machine:**

- Управление состояниями `WifiConnecting → Provisioning → Registering → AwaitingClaim → Ready → MqttConnecting → Online`.
- Отправка текущего состояния в MCU через `Heartbeat.cloudState`.

### Что LINK получает из библиотеки

Готовые компоненты (запомнить каждый не нужно — они будут подробно представлены в quickstart-ах и в разделах протокола; здесь — просто список и схема связей):

- `DryerUart::UartBridge` — парсинг и формирование UART-кадров.
- `idryer::MqttClient` — MQTT-клиент.
- `idryer::HttpApi` — HTTP-клиент портала.
- `idryer::cloud::CommandHandler` — разбор команд.
- `idryer::cloud::CloudStateMachine` — автомат состояний.
- `idryer::TelemetryPublisher` — формирование JSON из UART-payload.

**Как они связаны:**

```
                        (входящие UART-кадры)
                                   ▼
                         ┌─────────────────┐
                  UART ──┤   UartBridge    ├── колбэки ──► прикладной код
                         └─────────────────┘
                                   ▲
                                   │ uart.sendCommand(...)
                                   │
                         ┌─────────────────┐
                         │ UartCommandSink │◄── sink ──┐
                         │  (реализация    │           │
                         │   ICommandSink) │           │
                         └─────────────────┘           │
                                                        │
  входящая MQTT-команда                                │
         │                                              │
         ▼                                              │
┌─────────────────┐     JSON    ┌─────────────────┐    │
│   MqttClient    │────────────►│ CommandHandler  │────┘
└─────────────────┘             └─────────────────┘
         ▲                              
         │ публикация телеметрии/статуса
         │                              
┌─────────────────┐   UART payload   ┌──────────────────┐
│TelemetryPublisher│◄───────────────│   UartBridge     │
└─────────────────┘   (колбэк)       │ (те же входящие) │
                                      └──────────────────┘

┌─────────────────┐     HTTP     ┌──────────────────┐
│    HttpApi      │◄────────────►│ CloudStateMachine│
└─────────────────┘              └──────────────────┘
                                          │
                                          │ cloudState → в Heartbeat MCU
                                          ▼
                                     UartBridge
```

`UartCommandSink` — готовая «переходная» реализация: `CommandHandler` разобрал JSON и зовёт `sink->sendCommand(...)`, а sink превращает это в UART-вызов через `UartBridge`. Для устройств без UART (standalone на одном ESP32) можно написать свою реализацию `ICommandSink`, которая применяет команду локально — подробно это в [../05-cloud/03-command-sink.md](../05-cloud/03-command-sink.md).

Прикладной код создаёт инстансы этих классов, передаёт один в другой через конструкторы (вот что будет в квикстарте как «соберите цепочку»), регистрирует колбэки на входящие UART-кадры и MQTT-команды, затем запускает главный цикл.

## Cloud (Portal)

### Кто это

Готовая инфраструктура iDryer: сервер Node.js (NestJS), база данных, MQTT-брокер (EMQX), веб и мобильное приложение. Публичная точка входа — `portal.idryer.org`.

### Задача

Связать устройства с аккаунтами пользователей и быть посредником между пользовательским UI и устройствами.

### Обязанности

- Принимать provision-запросы от новых устройств, выдавать `deviceToken`.
- Принимать register-запросы, выдавать PIN.
- Принимать claim-запросы от приложений пользователей, связывать устройство с аккаунтом.
- Принимать телеметрию от устройств и показывать её в UI.
- Принимать команды пользователя в UI и публиковать их в MQTT-топики устройства.
- Вести учёт устройств и пользователей в БД.

### Что Cloud предоставляет разработчику устройства

- Публичный HTTP API (без аутентификации для provision/register).
- MQTT-брокер с проверкой `(serialNumber, deviceToken)` через HTTP auth hook.
- Набор топиков с фиксированными префиксами и именами.
- Форматы JSON для телеметрии и команд.

### Что Cloud **не делает**

- Не знает, как устроен ваш контроллер внутри.
- Не навязывает свой UI — вы можете использовать и веб-портал, и приложение, и сторонних клиентов.
- Не хранит пользовательские настройки меню — они живут на MCU.
- Не знает прошивку LINK или MCU — взаимодействует только по контракту.

## Граница «библиотека ↔ прикладная прошивка LINK»

Это источник частой путаницы. Ниже — жёсткая граница.

### Делает библиотека

- Формирование и парсинг UART-кадров.
- MQTT-клиент: подключение, LWT, подписка, публикация.
- HTTP-клиент: provision / register / check-claim.
- `CommandHandler` — парсинг входящих MQTT-команд и **преобразование** их в UART-структуры (не отправка — см. ниже).
- `CloudStateMachine` — автомат состояний подключения.
- `TelemetryPublisher` — формирование JSON для публикации из UART-payload.

### Должна делать прикладная прошивка LINK

- Создать инстансы компонентов и соединить их (dependency injection).
- Реализовать `ICommandSink` — «куда отправлять разобранные команды». Для классической конфигурации с UART библиотека даёт готовый `UartCommandSink` (отправляет через `UartBridge`).
- Регистрировать колбэки для входящих UART-кадров (где что делать при `Telemetry`, `Log`, `ClaimStart`, …).
- Решать, **когда** публиковать. Например, `Log` (0x60) по UART **не** публикуется в MQTT автоматически — нужен колбэк, который вызовет `MqttClient::publishEvent`.
- Хранить в NVS `deviceToken` и `serialNumber`.
- Управлять экраном/меню, если модуль имеет локальный UI (в обычной LINK-конфигурации этим занимается MCU).

### Типичный пример путаницы

> «Почему в MQTT нет `events` от моих ошибок?»

Потому что `UartBridge` при приёме `Log` (0x60) вызывает только зарегистрированный `logHandler_`. Если прикладной код не вызвал `setLogHandler(...)` и внутри него не вызвал `MqttClient::publishEvent(...)`, то в `events` ничего не пойдёт. Это **не баг библиотеки** — это зона ответственности прошивки.

Референсная прошивка iDryer Link делает это в `IdryerDevice::handleLog`. Ваша прошивка должна сделать то же самое, если вам нужна публикация в `events`.

## Разделение «продукт iDryer Link» vs «библиотека idryer-protocol»

| Артефакт | Что это | Где лежит |
|----------|---------|-----------|
| **iDryer Link** | Референсная потребительская прошивка для ESP32-модуля (с экраном, меню, staging-скриптами) | Отдельный репозиторий [idryer-link](https://github.com/pavluchenkor/idryer-link) |
| **idryer-protocol** | Библиотека, на которой построен Link. Доступна как `lib_deps` в PlatformIO | Этот репозиторий |

Если вы **разрабатываете своё устройство**, вам достаточно `idryer-protocol`. Link можно смотреть как живой пример использования библиотеки.
