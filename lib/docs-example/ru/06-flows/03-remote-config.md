# Remote config: настройки меню через облако

Пользователь открывает приложение, меняет настройку в меню устройства — значение должно уйти на MCU, примениться, сохраниться в EEPROM, вернуться подтверждение. И наоборот: устройство шлёт полный конфиг в облако, чтобы приложение показало актуальные значения.

MCU — источник истины для настроек. LINK только пересылает.

---

## Основные понятия

- **Полный конфиг** — весь JSON меню (`{"v":8,"units":3,"active":0,"lang":"en","menu":[...]}`), до ~3 КБ. Публикуется в `idryer/<serial>/config`.
- **Delta** — инкрементальное изменение одного элемента (`{"d":{"3":[55,60,55]}}`). Публикуется в `idryer/<serial>/config/delta`.
- **set** — команда от облака: «измени параметр с ID=3 на значение X».
- **invoke** — команда от облака: «выполни action с ID=5» (например, «сохранить в EEPROM», «восстановить заводские»).
- **UART `ConfigPush` (0x30)** — транспорт для всех трёх: полного JSON, delta, set/invoke.
- **rev** — номер ревизии конфига на MCU, инкрементируется при каждом изменении; гарантирует консистентность.

---

## Сценарий 1: устройство публикует полный конфиг

Когда это происходит:

- Пользователь впервые открыл приложение устройства.
- Приложение послало `commands/get_config`, устройство отвечает.
- Прошивка обновилась — меню могло поменяться.

### Последовательность

```
App  ──MQTT publish commands/get_config──►  LINK
LINK ──UART Command{GetConfig}──►  MCU
MCU  ──UART ConfigPush (фрагментированный)──►  LINK
     [фрагмент 1 из N, FLAG_FRAGMENTED]
     [фрагмент 2 из N, FLAG_FRAGMENTED]
     ...
     [фрагмент N, FLAG_LAST_FRAGMENT]
LINK ──собирает полный JSON──►  ...
LINK ──MQTT publish idryer/<serial>/config──►  Broker
```

Фрагментация: каждый чанк — `ConfigChunkPayload` (6 байт header + до 194 байт data). Подробно — [../03-uart/05-ack-retry.md](../03-uart/05-ack-retry.md) и [../03-uart/06-examples.md](../03-uart/06-examples.md).

### Формат полного JSON

```json
{
  "v": 8,
  "units": 3,
  "active": 0,
  "lang": "en",
  "menu": [
    { "id": 3, "t": "val", "val": [50, 65, 85] },
    { "id": 5, "t": "val", "val": [40, 15] },
    { "id": 17, "t": "val", "val": [55, 60, 55] }
  ]
}
```

- `v` — версия схемы конфига (и/или текущий `rev`).
- `units` — количество активных камер.
- `active` — индекс текущей активной камеры (0-based).
- `lang` — `"en"` / `"ru"`.
- `menu[]` — список элементов меню. Поле `val` может быть числом или массивом (по элементу на каждую камеру).

Определение, какие id у каких элементов и их типы — в заголовке `menu_meta.h`, общем для MCU и LINK. Эту синхронизацию обеспечивает сборка обеих прошивок из одного репозитория библиотеки.

## Сценарий 2: пользователь меняет значение (set)

Пользователь в приложении выбирает «целевая температура камеры U1 = 55 °C».

```
App  ──MQTT publish commands/set──►  LINK
     { "id": 3, "unit": 0, "val": 55 }

LINK: парсер → CommandHandler.handleSet → sink.sendConfigPushChunk(...)

LINK ──UART ConfigPush──►  MCU
     data = {"cmd":"set","id":3,"unit":0,"val":55}
     (если JSON ≤ 194 байт — один кадр с FLAG_LAST_FRAGMENT)

MCU: применяет, инкрементирует rev, сохраняет в EEPROM.

MCU  ──UART ConfigPush (delta)──►  LINK
     data = {"d":{"3":[55,60,55]}}

LINK ──MQTT publish idryer/<serial>/config/delta──►  Broker
     {"d":{"3":[55,60,55]}}
```

Delta содержит только изменённые элементы; если изменилась одна ячейка массива, MCU всё равно шлёт весь массив для этого id (чтобы приложение видело текущее полное значение).

## Сценарий 3: пользователь вызывает action (invoke)

Например, «восстановить заводские настройки для камеры».

```
App  ──MQTT publish commands/invoke──►  LINK
     { "id": 7 }

LINK ──UART ConfigPush──►  MCU
     data = {"cmd":"invoke","id":7}

MCU: выполняет action, инкрементирует rev, публикует итоговый delta всех изменений.

MCU  ──UART ConfigPush (delta)──►  LINK
     data = {"d":{"3":[50,50,50],"5":[40,15],"17":[55,55,55]}}

LINK ──MQTT publish idryer/<serial>/config/delta──►  Broker
```

Для `invoke`, затрагивающего много элементов, delta может быть большой — если выходит за 194 байта, потребовалась бы фрагментация. В референсной прошивке MCU фрагментирует свои delta нормально (`UartBridge.sendConfigPushChunk`).

---

## Ограничения

### Большие set/invoke из MQTT

Если JSON из облака (`{"cmd":"set","id":9,"unit":0,"val":[1,2,3,…]}`) превышает `CONFIG_CHUNK_DATA_SIZE = 194` байта, в референсной прошивке **LINK не фрагментирует** исходящий `ConfigPush` — логируется «fragmentation not implemented». Это известное ограничение. Для обычных настроек (числа и короткие массивы) лимита достаточно.

### Большие конфиги от MCU к облаку

MCU фрагментирует корректно. Публикация в MQTT `config` — одним сообщением целиком. Лимит MQTT-буфера — 16 КБ (см. [../04-mqtt/01-connection.md](../04-mqtt/01-connection.md)). Полный конфиг на 4 камеры редко превышает 3 КБ.

### Идентификаторы и семантика

`id` элемента меню — плоский индекс, заданный в `menu_meta.h`. При добавлении новых элементов в прошивке изменяется только этот заголовок. Версионирование через `v` или `rev` помогает приложению обнаружить рассинхронизацию и перезапросить полный конфиг.

---

## Версионирование конфига

```
Event          rev       Action
──────────────  ──────    ──────────────────────────────────
boot            loaded from EEPROM
MQTT set        rev++     delta published
MQTT invoke     rev++     delta published
OTA update      reset     полный конфиг по GetConfig
```

Если приложение долго было оффлайн и после подключения получает retained-`config` с другим `v`/`rev` — должно перезапросить полный `get_config`.
