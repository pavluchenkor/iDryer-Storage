# Глоссарий терминов и идентификаторов

Единый словарь для всей документации. Если где-то в тексте встретился незнакомый термин — ищите здесь.

---

## Узлы системы

### MCU

**M**icro**C**ontroller **U**nit. Контроллер сушилки — отдельная плата с микроконтроллером, управляющая железом (нагреватель, датчики, экран, EEPROM). В референсной прошивке — RP2040, но библиотека не привязана к конкретному чипу. Синонимы: **Controller**, **RP2040** (в контексте референсной прошивки).

### LINK

Сетевой модуль на базе ESP32. Даёт устройству WiFi, MQTT, HTTP-клиент. Реализован как прошивка поверх библиотеки `idryer-protocol`. Синонимы: **Network module**, **ESP32** (в контексте референсной прошивки), **bridge** (когда подчёркивается его роль моста UART ↔ MQTT).

### Cloud / Portal / Backend

Серверная инфраструктура iDryer. Включает в себя REST API, MQTT-брокер, базу устройств и пользователей, веб и мобильное приложение. Публичная точка входа: [portal.idryer.org](https://portal.idryer.org).

- **Portal** — когда речь про REST API или веб-интерфейс.
- **Backend** — когда речь про серверный код.
- **Cloud** — общее название.

### Unit

Одна камера сушилки. Имеет свой нагреватель, свои датчики, свой режим работы. В устройстве может быть 1–4 unit-а.

- В UART индексируется как `unitId: 0, 1, 2, 3`.
- В MQTT передаётся как строка: `U1, U2, U3, U4`.
- Значение `0xFF` в UART означает «все unit-ы» (для команды `stop`).

## Идентификаторы

### serialNumber

Уникальный идентификатор **модуля LINK**. Именно он используется:

- как префикс всех MQTT-топиков: `idryer/<serialNumber>/...`,
- как `Client ID` при подключении к брокеру,
- как `username` MQTT-авторизации,
- в теле запроса `POST /devices/provision`.

**Формат** (валидация портала):

- `DEVICE_<mac>` или `DEVICE_<mac>_<suffix>` — типичная форма для ESP32-модуля на базе MAC-адреса WiFi,
- либо ровно 16 hex-символов (для standalone-устройств, где MAC не подходит, например, когда MCU один за всё).

**Примеры:**

```
DEVICE_aabbccddeeff
DEVICE_aabbccddeeff_1234567
36B955AB4350FEDC
```

**Источник:** прошивка LINK сама формирует при первом старте и сохраняет в NVS. На рабочем устройстве стабилен на всю жизнь.

### mcuSerial

Уникальный идентификатор **контроллера** (MCU). Передаётся внутри `HelloPayload.mcuSerial` (17 байт: 16 hex + `\0`). Для RP2040 — hex flash ID чипа.

**Не путать с `serialNumber`:**

- `serialNumber` — у LINK, для облака.
- `mcuSerial` — у MCU, для диагностики.

LINK пробрасывает `mcuSerial` в MQTT-топик `info` как отдельное поле JSON. Портал **не использует** его для идентификации устройства — это справочная информация.

### deviceToken

Секретный токен MQTT-авторизации LINK. Выдаётся порталом в ответ на `POST /devices/provision`.

**Как живёт:**

- LINK сохраняет в NVS.
- Используется как **password** при подключении к MQTT-брокеру.
- Брокер проверяет пару `(serialNumber, deviceToken)` через HTTP auth hook backend-а.

**Не путать с user JWT:**

- `deviceToken` выдаётся устройству без аутентификации и нужен для MQTT устройства.
- User JWT выдаётся пользователю после логина в приложении и нужен для `POST /devices/claim`.

Если устройство уже привязано (`isClaimed: true`), повторный provision возвращает `deviceToken: null` — это защита от подмены. Устройство в этом случае должно провести пользователя через сценарий recovery (удалить устройство в приложении, затем привязать снова).

### deviceId

UUID устройства в базе данных портала. Создаётся при успешном claim.

**Используется:**

- LINK получает его в ответе `GET /devices/check-claim/:token` после успешного claim.
- MCU получает его в `ClaimCompletePayload.deviceId` — **только для отображения на экране**.
- Приложение использует его при работе с API портала.

**Не используется** в MQTT-топиках и в MQTT-авторизации. Для MQTT достаточно `serialNumber` + `deviceToken`.

### User JWT

JSON Web Token, получаемый пользователем при логине в приложении портала. Содержит ID пользователя, срок действия, подпись. Используется как `Authorization: Bearer <jwt>` при вызове `POST /devices/claim` из приложения.

**Устройству (LINK) JWT не нужен.** Устройство живёт на `deviceToken`.

### PIN (claiming)

Восьмизначный код, выдаваемый порталом устройству в ответ на `POST /devices/register`. TTL — 10 минут. Пользователь видит PIN на экране сушилки и вводит его в приложение, чтобы привязать устройство к своему аккаунту.

Отдельный **PIN для WebSocket** (4 цифры, 0–9999) — это другая сущность, не путать. См. [../07-features/02-websocket-local.md](../07-features/02-websocket-local.md).

## Протоколы и форматы

### UART-кадр (Frame)

Единица обмена по UART. Состоит из заголовка (`FrameHeader`, 6 байт), payload (0–200 байт) и двух байт CRC. Начинается с SOF = `0xAA`. Подробно — [../03-uart/02-frame-and-crc.md](../03-uart/02-frame-and-crc.md).

### MessageKind

Тип UART-кадра (`enum uint8_t`). Определяет, как интерпретировать payload. Например: `Hello = 0x01`, `Telemetry = 0x10`, `Command = 0x20`. Полный список — [../03-uart/03-message-types.md](../03-uart/03-message-types.md).

### Payload

Полезная нагрузка UART-кадра. Структура зависит от `MessageKind`. Все payload-структуры упакованы `#pragma pack(1)`, все многобайтовые значения — little-endian. Подробно — [../03-uart/04-binary-structures.md](../03-uart/04-binary-structures.md).

### CRC16-CCITT

Контрольная сумма UART-кадра. Полином `0x1021`, начальное значение `0xFFFF`, результат пишется в кадр little-endian (младший байт первым). Референсная реализация в `src/uart/uart_protocol.cpp`.

### SEQ (sequence)

Номер последовательности кадра (`uint8_t`, 0–255, инкремент при каждом отправленном кадре). В `ACK`-кадре `SEQ` равен номеру подтверждаемого кадра.

### ACK / ACK_REQUIRED

Механизм подтверждения доставки. Отправитель ставит флаг `ACK_REQUIRED = 0x01` в заголовке. Получатель отвечает ACK-кадром (`TelemetryAck = 0x11`, `CommandAck = 0x21`, `ConfigAck = 0x31`) с соответствующим `SEQ`. Timeout — 700 мс, до 3 повторов. Подробно — [../03-uart/05-ack-retry.md](../03-uart/05-ack-retry.md).

### Heartbeat

Периодический «я жив» кадр. Отправляется обеими сторонами раз в 5 секунд. Несёт uptime, RSSI (или температуру MCU), счётчик ошибок и текущее состояние облака. Структура `HeartbeatPayload`.

### Provision / Register / Claim / Check-claim

Этапы привязки устройства:

- **Provision** — LINK получает `deviceToken`.
- **Register** — LINK получает PIN, показывает пользователю.
- **Claim** — пользователь вводит PIN в приложение, приложение вызывает `POST /devices/claim`.
- **Check-claim** — LINK поллит портал, чтобы узнать, завершил ли пользователь привязку.

Подробно — [../05-cloud/01-claiming-overview.md](../05-cloud/01-claiming-overview.md).

## Режимы работы MCU

Перечисление `DryerMode` в UART:

| Значение | Имя | Описание |
|----------|-----|----------|
| `0` | `Idle` | Устройство бездействует |
| `1` | `Drying` | Обычная сушка (температура + длительность) |
| `2` | `Storage` | Режим хранения (температура + влажность, без времени) |
| `3` | `Profile` | Многоэтапный профиль |
| `4` | `Fault` | Ошибка |

В MQTT эти значения передаются как строки: `"IDLE"`, `"DRYING"`, `"STORAGE"`, `"PROFILE"`, `"FAULT"`.

Отдельный `DryerState` (Idle/Preheat/Drying/Cooling/Fault/Service) — более детальное внутреннее состояние MCU. В библиотеке объявлен, но в референсном protocol-слое не используется: отправляется `DryerMode`, а не `DryerState`.

## Состояния облачного подключения

Перечисление `LinkCloudState` в `HeartbeatPayload.cloudState`:

| Значение | Имя | Описание |
|----------|-----|----------|
| `0` | `Idle` | Начальное состояние до `begin()` |
| `1` | `WifiConnecting` | Подключается к WiFi |
| `2` | `Provisioning` | Выполняет `POST /provision` |
| `3` | `Registering` | Выполняет `POST /register` |
| `4` | `AwaitingClaim` | Ждёт, пока пользователь введёт PIN |
| `5` | `Ready` | Получены WiFi + token + deviceId |
| `6` | `MqttConnecting` | Подключается к MQTT |
| `7` | `Online` | Всё работает |

MCU использует эти значения для индикации (LED/экран).

## MQTT-термины

### Префикс топиков

Все топики устройства начинаются с `idryer/<serialNumber>/`. Например: `idryer/DEVICE_aabb.../telemetry`.

### LWT (Last Will and Testament)

Механизм MQTT: если соединение обрывается неожиданно (без `DISCONNECT`), брокер сам публикует заранее заданное сообщение. LINK настраивает LWT на топик `idryer/<serial>/offline` с телом `{}`. Это позволяет серверу знать, что устройство ушло в оффлайн по сетевой причине, а не штатно.

### QoS

Уровень гарантии доставки MQTT: 0 (fire-and-forget), 1 (at-least-once), 2 (exactly-once). В iDryer используется QoS 0 для телеметрии (потери допустимы) и QoS 1 для остального.

### Retained

Флаг MQTT: «сохранить последнее сообщение, отдавать новым подписчикам». В iDryer используется для `info`, `status`, `rfid` — чтобы новый клиент (веб, приложение) сразу видел актуальные данные без ожидания следующей публикации.

## Единицы измерения и форматы

### Температура

- В UART: `int16`, значение × 10 (`553` означает `55.3 °C`). Позволяет передавать дробное значение без `float`.
- В MQTT (JSON): `float` с одним знаком после запятой (`55.3`).

### Влажность

- В UART: `uint16`, значение × 10 (`452` означает `45.2%`).
- В MQTT: `float` с одним знаком.

### Вес

- В UART: `uint16`, значение × 10 граммов (`1234` означает `123.4 г`). Диапазон до 5000 (500 г).
- В MQTT: `float` в граммах.

### Время

- UART в секундах (`uint32`), JSON-команды в секундах или минутах (по полю).
- Временные метки в JSON — ISO 8601 в UTC (например, `"2026-04-01T12:00:00Z"`).

### Версия прошивки

Упакована в `uint32`: `(MAJOR << 16) | (MINOR << 8) | PATCH`. Например, версия `1.2.3` = `0x00010203`.

## MQTT-термины за 5 минут

Для тех, кто публиковал телеметрию на ThingSpeak, но не копал глубже.

### QoS (Quality of Service)

Уровень гарантии доставки одного сообщения:

- **QoS 0** — «at most once», fire-and-forget. Отправил → забыл. Если потерялось — никто не узнает. Самый быстрый. Используется для `telemetry` (следующая через 5 сек всё равно придёт).
- **QoS 1** — «at least once». Отправитель повторяет, пока не получит PUBACK от получателя. Сообщение точно придёт, но **может прийти дважды**. Используется для `status`, `info`, `commands/*`.
- QoS 2 — в iDryer не используется (дороже по трафику без значимой пользы).

### Retained

Флаг на publish-сообщении. Если `true`, брокер **сохраняет** это сообщение и **отдаёт каждому новому подписчику** при подписке, без ожидания следующей публикации.

Пример: приложение пользователя подключилось к порталу → подписалось на `idryer/<serial>/info` → мгновенно получило retained-сообщение «вот такое устройство, версия прошивки 1.2.3, вот камеры», даже если устройство сейчас вообще не публикует.

В iDryer `retained: true` у `info`, `status`, `rfid`, `integrations/status` — всё, что описывает «текущее состояние».

### Keepalive

Интервал в секундах между ping-ами клиента (default 60). Если клиент не шлёт данные и не `PINGREQ`, брокер после keepalive-таймаута считает его **мёртвым**, закрывает сессию и (при наличии) публикует LWT.

На клиенте PubSubClient сам шлёт `PINGREQ` каждые ~45 сек. Если WiFi плохой — пакет может потеряться, и брокер отрубит сессию.

### LWT (Last Will and Testament)

«Завещание» клиента. При подключении клиент говорит брокеру: «если я вдруг отвалюсь аварийно — опубликуй за меня **вот это**». Брокер публикует заданное сообщение в заданный топик **только** при аварийном разрыве (не при штатном `disconnect`).

iDryer использует LWT для топика `idryer/<serial>/offline` с телом `{}` — чтобы backend сразу узнавал о падении устройства (не ждал keepalive-таймаута).

### Clean session / Persistent session

Флаг в пакете CONNECT. Определяет, **помнит ли брокер клиента** между реконнектами.

- **`clean_session = true`** — каждый CONNECT начинается с чистого листа. Подписка стирается, накопленные QoS 1 сообщения теряются. По протоколу обозначается как `c1`.
- **`clean_session = false`** — брокер держит для этого `clientId` подписку и очередь QoS 1 сообщений. При обрыве связи команды не теряются. Обозначается как `c0`.

В iDryer всегда `clean_session = false` — иначе при каждом реконнекте клиент рискует не успеть переподписаться (пакет SUBSCRIBE может пропасть в WiFi-лагах), и команды от портала перестанут приходить.

### Wildcard `+` и `#`

В подписках MQTT можно использовать подстановочные знаки:

- `+` — **один уровень**: `idryer/+/telemetry` совпадёт с `idryer/DEV_AAA/telemetry`, `idryer/DEV_BBB/telemetry`, но не с `idryer/DEV_AAA/sub/telemetry`.
- `#` — **всё вложенное**: `idryer/DEV_AAA/commands/#` совпадёт с `idryer/DEV_AAA/commands/drying`, `commands/stop`, и т.д. Только в **конце** топика.

Устройство подписывается на `idryer/<serial>/commands/#` — получает все команды.

### TLS (Transport Layer Security)

Шифрование + аутентификация поверх TCP. В iDryer MQTT идёт через TLS на порту 8883 (а не plain 1883).

Клиенту нужен **корневой сертификат (CA)** того удостоверяющего центра, который подписал сертификат сервера. В коде это `WiFiClientSecure` + `setCACert(ROOT_CA_LETSENCRYPT)`. Для Let's Encrypt CA хранится прямо в прошивке.

Для LAN-соединений (например Bambu Lab принтер с self-signed cert) допустимо `setInsecure()` — клиент не проверяет сертификат сервера. В LAN это ок, в интернете — никогда.

## Веб-термины за 5 минут

### JWT (JSON Web Token)

Подписанный JSON-токен для HTTP-авторизации. Формат: `header.payload.signature` через точки (в base64). В заголовке HTTP передаётся как `Authorization: Bearer <jwt>`.

В iDryer **устройству** JWT не нужен (оно аутентифицируется `deviceToken`-ом по MQTT). JWT нужен только пользователю портала — приложение получает его при логине и использует для `POST /devices/claim`.

### REST API

HTTP + JSON по договору: методы `GET/POST/PUT/DELETE`, тело — JSON. iDryer-портал предоставляет REST-endpoint-ы `/devices/provision`, `/devices/register`, `/devices/claim`, `/devices/check-claim/:token`. ESP32 вызывает их через `HTTPClient` (c TLS для продакшена).

### mDNS (multicast DNS)

Протокол автообнаружения в локальной сети. Позволяет обращаться к устройствам по именам вида `myhost.local` без настройки DNS-сервера. Работает через мультикаст-запросы в пределах одной подсети.

iDryer использует mDNS для поиска Home Assistant (`homeassistant.local`) и, опционально, для Klipper/Moonraker (`klipper.local`). На ESP32 работает через библиотеку `ESPmDNS`.

### WebSocket

Двусторонний постоянный канал поверх TCP (RFC 6455). В отличие от HTTP «запрос → ответ», WebSocket — это «откры́ли соединение → шлём пакеты в обе стороны как хотим, пока не закрыли».

Используется для:

- Локального WS-сервера на LINK для приложения пользователя без облака (раздел [../07-features/02-websocket-local.md](../07-features/02-websocket-local.md)).
- Клиента к Moonraker (`ws://klipper.local:7125/websocket`) для подписки на статус Klipper в реальном времени.

### JSON-RPC 2.0

Формат удалённых вызовов через JSON-сообщения:

```json
// Запрос
{ "jsonrpc": "2.0", "method": "printer.objects.query", "params": {...}, "id": 1 }
// Ответ (успех)
{ "jsonrpc": "2.0", "result": {...}, "id": 1 }
// Уведомление (без id, сервер → клиент, без ответа)
{ "jsonrpc": "2.0", "method": "notify_status_update", "params": [...] }
```

Поверх WebSocket — это API Moonraker. Поле `id` матчит запрос с ответом; уведомления `id` не имеют.

### SSE (Server-Sent Events)

Однонаправленный канал «сервер → клиент» поверх HTTP. Сервер держит long-lived ответ и шлёт событие за событием. В отличие от WebSocket — нельзя отправить от клиента к серверу в том же соединении.

В iDryer не используется самим устройством, но портал может использовать SSE для push-обновлений статуса в UI браузера.

### NVS (Non-Volatile Storage)

Энергонезависимая память ESP32. Аналог EEPROM. Key-value хранилище, разделённое на namespaces. Используется через API `Preferences.h`. В iDryer хранит: `serialNumber`, `deviceToken`, WiFi credentials, настройки LINK-интеграций.

Namespace — это «папка» ключ-значение. Имя namespace ≤15 символов. В iDryer:

- `idryer` — основные credentials.
- `li_ha`, `li_bambu`, `li_moon`, `li_common` — настройки LINK-интеграций.
- `ha` — legacy Home Assistant настройки (через mDNS).

### ACL (Access Control List)

Правила брокера MQTT «кому на какой топик можно публиковать / подписываться». В Mosquitto задаются файлом `acl_file`. В iDryer устройству `<serial>` разрешено публиковать/подписываться только в `idryer/<serial>/...`.

## Аббревиатуры

| Сокращение | Расшифровка |
|------------|-------------|
| MCU | MicroController Unit — контроллер |
| LINK | ESP32-модуль, мост UART ↔ облако |
| LE | Little-Endian — порядок байтов, младший первый |
| SOF | Start Of Frame — стартовый байт UART-кадра (`0xAA`) |
| CRC | Cyclic Redundancy Check — контрольная сумма |
| ACK | Acknowledgement — подтверждение |
| NVS | Non-Volatile Storage — энергонезависимая память ESP32 |
| LWT | Last Will and Testament — «завещание» MQTT-клиента |
| RSSI | Received Signal Strength Indicator — сила сигнала WiFi |
| TTL | Time To Live — срок действия |
| PIN | Personal Identification Number — код для claim или WS |
| JWT | JSON Web Token — токен пользователя портала |
| QoS | Quality of Service — уровень гарантии MQTT |
| UUID | Universally Unique Identifier — `deviceId` |
| EEPROM | Постоянная память MCU для пользовательских настроек |
| WS | WebSocket — локальный канал без облака |
