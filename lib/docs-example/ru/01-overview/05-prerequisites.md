## 1. Типы фиксированного размера

В обычном Arduino-коде вы пишете `int x;`. На ESP32 `int` это 32 бита (4 байта), на классическом Arduino Uno — 16 бит (2 байта). Для **бинарного протокола это катастрофа**: размер поля должен быть одинаковым на обеих сторонах.

Поэтому везде используются явные типы из `<stdint.h>`:

| Тип | Размер | Диапазон |
|-----|--------|----------|
| `uint8_t` | 1 байт | 0 … 255 |
| `int8_t` | 1 байт | −128 … 127 |
| `uint16_t` | 2 байта | 0 … 65 535 |
| `int16_t` | 2 байта | −32 768 … 32 767 |
| `uint32_t` | 4 байта | 0 … 4 294 967 295 |
| `int32_t` | 4 байта | −2 147 483 648 … 2 147 483 647 |

Правило простое: **в UART-кадрах используйте только эти типы**, никогда не `int` / `short` / `long` без `_t`. Размер должен быть определён однозначно.

## 2. Битовые операции `<<`, `>>`, `&`, `|`

Четыре оператора на одно число. Не страшные, но легко спутать:

### Сдвиги

`x << n` — сдвиг **влево** на `n` бит. По сути: умножение на `2^n`.
`x >> n` — сдвиг **вправо**. Деление на `2^n`.

```cpp
uint8_t a = 0b00000001;   // = 1
uint8_t b = a << 3;       // 0b00001000 = 8
uint8_t c = b >> 2;       // 0b00000010 = 2
```

### Маски — `&` (И) и `|` (ИЛИ)

`a & b` — бит равен 1, только если **оба** бита равны 1.
`a | b` — бит равен 1, если **хотя бы один** равен 1.

Примеры из реальной библиотеки:

```cpp
// Собрать версию прошивки 1.2.3 в одно 32-битное число:
uint32_t firmware = (1u << 16) | (2u << 8) | 3u;
// Результат (в HEX): 0x00010203

// Извлечь MINOR из такого числа:
uint8_t minor = (firmware >> 8) & 0xFF;
//   >> 8   — сдвинули младший MINOR в младший байт
//   & 0xFF — обрезали лишнее (маска «оставить младший байт»)
```

### Проверка отдельного бита

```cpp
uint16_t capabilities = 0x001B;   // 0b00000000_00011011
bool hasHeater = (capabilities & (1 << 0)) != 0;  // проверяем бит 0
bool hasFan    = (capabilities & (1 << 1)) != 0;  // проверяем бит 1
```

`(1 << 0)` = 0b00000001, `(1 << 1)` = 0b00000010 и т.д. — это «маска одного бита».

## 3. Little-endian (порядок байтов)

Многобайтовое число в памяти можно хранить двумя способами:

- **Big-endian**: старший байт первым (как мы пишем числа — слева направо).
- **Little-endian**: **младший** байт первым.

ESP32 и большинство современных MCU — **little-endian**. Весь UART-протокол iDryer — little-endian.

### На пальцах

Число `uint16_t x = 0x1234` в памяти:

```
big-endian (не наш случай):    0x12  0x34
little-endian (наш случай):    0x34  0x12
                               ^^^^
                               младший байт
```

Число `uint32_t x = 0x12345678`:

```
little-endian:   0x78  0x56  0x34  0x12
                  LSB                MSB
```

### Практика

Отправляете `uint16_t temperatureC10 = 553` (55.3 °C × 10):

- `553` в hex = `0x0229`.
- По проводу идёт: `0x29`, затем `0x02`.

Принимая байты, собрать обратно:

```cpp
uint16_t t = buf[0] | (buf[1] << 8);   // 0x29 | (0x02 << 8) = 0x0229 = 553
```

Или через `memcpy`, потому что ESP32 сам по себе little-endian:

```cpp
uint16_t t;
memcpy(&t, buf, sizeof(t));   // копируем 2 байта, получаем правильное значение
```

### Зачем числа × 10

Видите в протоколе `temperatureC10`, `humidityPct10`, `weightGramsC10` — это **фиксированная точка**:

- `float` занимает 4 байта и иногда капризничает на разных платформах.
- Вместо этого держим целое число, умноженное на 10.
- `553` вместо `55.3`, передали как `int16` — 2 байта, детерминированно.
- На приёме: `float temp = raw / 10.0f;`.

## 4. `#pragma pack(1)` — упакованные структуры

По умолчанию компилятор **вставляет лишние байты** между полями структуры, чтобы числа лежали на «правильных» адресах (выравнивание). Это ускоряет доступ, но **ломает** бинарный протокол — размер структуры становится больше, чем сумма полей, и он разный на разных платформах.

Пример:

```cpp
struct Wrong {
    uint8_t  a;        // 1 байт
    uint32_t b;        // 4 байта
};
// sizeof(Wrong) == 8 (три байта паддинга между a и b!)
```

Чтобы **запретить** паддинг:

```cpp
#pragma pack(push, 1)
struct Right {
    uint8_t  a;        // 1 байт
    uint32_t b;        // 4 байта
};
#pragma pack(pop)
// sizeof(Right) == 5 (ровно сумма полей)
```

Все структуры payload в `idryer-protocol` обёрнуты в `#pragma pack(1)` — поэтому `sizeof(HelloPayload) == 86`, а не 88 или 92. Без этого устройство на одной платформе и устройство на другой **поняли бы разную длину кадра**.

## 5. `enum class`

Обычный C-style enum — просто именованные числа:

```cpp
enum MessageKind { Hello = 1, Telemetry = 10 };
int x = Hello;   // неявно преобразуется в int — опасно
```

`enum class` (C++11+) — **типизированный** enum:

```cpp
enum class MessageKind : uint8_t { Hello = 0x01, Telemetry = 0x10 };

MessageKind k = MessageKind::Hello;           // обращение через ::
// int x = k;                                  // ОШИБКА компиляции!
uint8_t raw = static_cast<uint8_t>(k);         // нужен явный каст
```

Плюсы:

- Типизация: не смешиваются разные enum-ы.
- Явный базовый тип (`: uint8_t` — ровно 1 байт, важно для протокола).
- Обращение через `::` делает код читаемее.

В коде библиотеки **везде** `enum class` с `: uint8_t` (или `: uint16_t`). Это не случайность — это часть бинарного контракта.

## 6. C-строки и padding нулями

В C/C++ строка — это массив `char`, заканчивающийся байтом `\0` (нулём).

```cpp
char s[8] = "Hello";   // 5 символов + '\0' на позиции 5 + ещё 2 байта на позициях 6,7
// В памяти: 'H' 'e' 'l' 'l' 'o' '\0' '\0' '\0'
```

В протоколе iDryer строковые поля имеют **фиксированный размер** — 8 / 17 / 32 / 100 байт. Контракт:

- Реальная строка + `\0`, остальное — нули до конца поля.
- На приёме: читаете до первого `\0`.

Это критично когда поле передаёт, например, 5-символьное имя в 32-байтовом слоте — остальные 27 байт **не мусор**, а ровно нули.

## 7. Ссылки `const T&`

В коде библиотеки вы увидите колбэки вида:

```cpp
void onHello(const HelloPayload& p, const FrameHeader& h) { ... }
```

`const HelloPayload& p` — это **ссылка на константу**. Две вещи:

- **Ссылка** (`&`) — не копия. Функция получает тот же объект что и вызывающий код. Это дёшево (не копируется 86 байт).
- **`const`** — менять через эту ссылку нельзя, только читать.

В вашей функции — работайте с `p` как с обычным объектом: `p.firmwareVersion`, `p.unitsCount`. Никаких `p->` — это ссылка, не указатель.

## 8. Колбэки — зачем передавать функцию в функцию

В Arduino вы привыкли: «вызвал `Serial.println` — напечаталось». Это **прямой** вызов.

В событийной библиотеке (а idryer-protocol такой): «зарегистрируй функцию → я вызову её, когда случится событие». Это **колбэк**.

```cpp
// 1. Определяете свою функцию с нужной сигнатурой:
void myOnTelemetry(const TelemetryPayload& p, const FrameHeader& h) {
    Serial.printf("T=%.1f\n", p.units[0].temperatureC10 / 10.0f);
}

// 2. Регистрируете её в библиотеке:
uartBridge.setTelemetryHandler(myOnTelemetry);

// 3. Всё. Теперь каждый раз когда прилетит Telemetry-кадр,
//    библиотека САМА вызовет вашу функцию. Вы `myOnTelemetry` не вызываете явно.
```

Можно передать лямбду (C++11 безымянная функция с захватом контекста):

```cpp
uartBridge.setTelemetryHandler([this](const TelemetryPayload& p, const FrameHeader& h) {
    this->handleIt(p);   // можно использовать 'this' из окружающего класса
});
```

Типично все `setXxxHandler(...)` методы принимают `std::function<void(...)>` — это универсальный тип «что-то вызываемое с такой сигнатурой». Вам главное — соблюсти **сигнатуру** (список параметров).

## 9. Namespaces (пространства имён)

В библиотеке типы лежат в пространствах имён:

- `DryerUart::` — UART-типы (`HelloPayload`, `FrameHeader`, `MessageKind`).
- `idryer::` — облачные типы (`MqttClient`).
- `idryer::cloud::` — cloud-контейнеры (`CommandHandler`, `LinkIntegrationsManager`).
- `idryer::hal::` — HAL-обёртки (`ArduinoSerial`).

Два способа обращения:

### Полный путь (verbose, но явно)

```cpp
DryerUart::HelloPayload req{};
req.role = DryerUart::Role::Rp2040Controller;
```

### Через `using namespace`

```cpp
using namespace DryerUart;   // обычно в начале .cpp файла

HelloPayload req{};          // теперь без DryerUart::
req.role = Role::Rp2040Controller;
```

Это **не «копирует» код**, просто компилятор начинает искать имена в этом пространстве.

!!! warning "Не в .h файлах"
    `using namespace` в заголовочных файлах — плохая практика (засоряет пространство имён у всех, кто включит заголовок). В `.cpp` — безопасно и удобно.

## 10. HAL, header-only и другие частые термины

Несколько «одних слов», которые часто встречаются:

- **HAL** (Hardware Abstraction Layer) — обёртка над платформо-зависимыми API. В нашей библиотеке `ArduinoSerial` — HAL-реализация интерфейса `ISerial` для Arduino-core. Смысл: ядро библиотеки не знает «Arduino» или «чистый ESP-IDF» — оно работает через интерфейс.

- **header-only** — библиотека/модуль, состоящий только из `.h`-файлов, без отдельного `.cpp`, который надо собирать. Подключил `#include` — и всё, линковка не нужна. UART-структуры из `uart_protocol.h` так и работают.

- **NVS** (Non-Volatile Storage) — энергонезависимая память ESP32. Аналог EEPROM. Используется через `Preferences.h`. Хранит `deviceToken`, настройки интеграций — всё, что должно пережить перезагрузку.

- **TLS** (Transport Layer Security) — шифрование поверх TCP. В коде видно как `WiFiClientSecure`. Для подключения к нужному серверу нужно передать корневой CA-сертификат (`setCACert(ROOT_CA)`), чтобы проверить подлинность сервера. `setInsecure()` — отключает проверку (только для LAN-устройств типа Bambu с самоподписанным сертификатом).

- **JWT** (JSON Web Token) — подписанный токен для HTTP-авторизации. Устройству **не нужен** (у него свой `deviceToken`), но приложение пользователя использует JWT для вызова `POST /devices/claim`.

- **mDNS** — «multicast DNS», автообнаружение устройств в локальной сети по именам вида `myhost.local`. Используется для поиска Home Assistant (`homeassistant.local`) и Klipper.

- **WebSocket** — двусторонний постоянный канал связи поверх TCP (RFC 6455). В отличие от HTTP — не «запрос/ответ», а открытый пайп. Используется в Moonraker для подписки на события Klipper.

- **JSON-RPC** — формат для удалённых вызовов через JSON-сообщения: клиент шлёт `{method, params, id}`, сервер отвечает `{result или error, id}`. Поверх WebSocket это как раз Moonraker-API.
