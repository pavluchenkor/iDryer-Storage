# Архитектура системы

Этот документ описывает, **кто с кем разговаривает, по какому каналу и с какими правилами**. После прочтения у вас должна быть мысленная карта: «вот три узла, вот три канала связи, вот что бегает по каждому каналу».

!!! note "Термины"
    Все идентификаторы, аббревиатуры и единицы измерения — в [04-glossary.md](04-glossary.md). Если встретится незнакомое сокращение (NVS, LWT, RSSI), посмотрите там.

## Три узла

```
┌─────────────┐           ┌─────────────┐           ┌─────────────┐
│     MCU     │   UART    │    LINK     │   MQTT    │   Cloud     │
│ Controller  │◄─────────►│ Net module  │◄─────────►│  (portal)   │
└─────────────┘           └─────────────┘           └─────────────┘
      │                         │                         ▲
      │                         │                         │ HTTP
      │                         └─────────────────────────┘
      │                            (только LINK → Cloud)
      │
      ▼
  Датчики,
  нагреватель,
  экран, EEPROM
```

| Узел | Физически | За что отвечает |
|------|-----------|------------------|
| **MCU** | Микроконтроллер внутри сушилки (типично RP2040, но любой Arduino-совместимый подойдёт) | Управление железом, датчики, PID, экран, EEPROM |
| **LINK** | Модуль WiFi (типично ESP32), на нём работает библиотека `idryer-protocol` | Связь с облаком, мост UART ↔ MQTT, claiming |
| **Cloud** | Сервер iDryer: REST API портала + MQTT-брокер + база данных | Хранение устройств, привязка к аккаунтам, маршрутизация команд |

**Упрощение:** для standalone-устройств (один ESP32 за всё) MCU и LINK объединены в один узел. Архитектурно это тот же контур: библиотека внутри работает так же.

## Три канала связи

### Канал 1: UART (MCU ↔ LINK)

**Физика:** обычный UART, 115200 бод, 8N1, без аппаратного контроля потока. Два провода на данные (TX/RX) + GND. Опционально — кабель питания.

**Что бегает:**

- MCU → LINK: телеметрия, статус, RFID-события, Hello при старте, Heartbeat, ошибки приложения (`Log`).
- LINK → MCU: команды с облака (Start/Stop/Profile/…), конфиг, PIN для привязки, статус сети.
- Обе стороны: `Heartbeat` раз в 5 секунд, `ACK` на запросы с флагом `ACK_REQUIRED`.

**Правила:**

- Каждый кадр начинается байтом `0xAA`, содержит CRC16, имеет номер последовательности.
- Надёжные запросы помечаются флагом `ACK_REQUIRED`. Если за 700 мс не пришёл ACK — retry, до 3 попыток.
- Длина payload — до 200 байт. Большие данные (JSON конфига) фрагментируются.

Подробно: [../03-uart/](../03-uart/).

### Канал 2: MQTT (LINK ↔ Cloud)

**Физика:** TLS-соединение с MQTT-брокером портала (в продакшене — порт 8883, CA-сертификат Let's Encrypt).

**Что бегает:**

- LINK → Cloud: телеметрия, статус, веса, RFID-события, события приложения, конфиг меню.
- Cloud → LINK: команды от пользователя (запуск сушки, остановка, настройки).

**Правила:**

- Все топики начинаются с `idryer/<serialNumber>/...`, где `serialNumber` — идентификатор модуля LINK.
- Пароль MQTT — это `deviceToken`, который LINK получает от портала один раз при первом подключении. Не «пользовательский пароль от портала» и не пароль WiFi.
- QoS и retained заданы по каждому топику (`info` — retained, `telemetry` — не retained и т.д.).

Подробно: [../04-mqtt/](../04-mqtt/).

### Канал 3: HTTP (LINK → Cloud)

**Физика:** HTTPS с публичным API портала, `portal.idryer.org/api`.

**Что бегает** (цепочка привязки устройства, «claiming» — подробности в [../05-cloud/01-claiming-overview.md](../05-cloud/01-claiming-overview.md)):

- `POST /devices/provision` — получить `deviceToken` для MQTT.
- `POST /devices/register` — получить PIN для пользователя.
- `GET /devices/check-claim/:token` — дождаться, пока пользователь привяжет устройство в приложении.

**Правила:**

- HTTP нужен **только при первом запуске** или после сброса NVS. В рабочем режиме устройство живёт в MQTT.
- Часть endpoint-ов не требует аутентификации (provision/register), часть требует JWT пользователя (claim — делает приложение, не устройство).

Подробно: [../05-cloud/](../05-cloud/).

## Кто инициирует связь

Это важно понимать сразу.

| Событие | Инициатор | Куда уходит |
|---------|-----------|-------------|
| Старт устройства | MCU → Hello → LINK | LINK триггерит MCU, если нужно |
| Телеметрия | MCU отправляет сам | LINK публикует в MQTT |
| Команда пользователя (Start/Stop/...) | Пользователь в app → Cloud → LINK → MCU | Всегда вниз по цепочке |
| Привязка устройства | MCU → ClaimStart → LINK | LINK идёт в HTTP |
| Heartbeat | Обе стороны (MCU и LINK) | Перекрёстно |

**Ключевое:** облако **не может** позвать контроллер напрямую. Всегда через LINK, всегда через MQTT. Если LINK оффлайн — устройство не управляется удалённо (но работает локально).

## Камеры (unit-ы)

Сушилка может иметь **1–4 камеры** (`unit`). Каждая камера — независимый контур: свой нагреватель, свои датчики, свой режим работы.

- `unitId` в UART: `0, 1, 2, 3`.
- В MQTT тот же индекс выводится как строка: `U1, U2, U3, U4`.
- Спец-значение `0xFF` в UART (`unitId = 0xFF`) означает «все камеры» — для команд типа `stop`.

Конфигурация камер (какие датчики, какие RFID-ридеры привязаны) передаётся один раз при старте — в структуре `HelloPayload`.

## Идентификаторы

В системе живут несколько идентификаторов, и их важно не путать:

| Идентификатор | Чей | Пример | Где используется |
|----------------|-----|--------|-------------------|
| `serialNumber` | LINK | `DEVICE_aabbccddeeff_1234567` | Префикс MQTT-топиков, username для брокера |
| `mcuSerial` | MCU | `36B955AB4350` (16 hex) | Идёт внутри Hello, пробрасывается в MQTT info |
| `deviceToken` | LINK | секретная строка | Пароль MQTT, хранится в NVS модуля |
| `deviceId` | Устройство в БД портала | UUID | Используется только для отображения |
| User JWT | Пользователь портала | JWT | Для `POST /devices/claim` из приложения, **не** для устройства |

Полные определения — в [04-glossary.md](04-glossary.md).
