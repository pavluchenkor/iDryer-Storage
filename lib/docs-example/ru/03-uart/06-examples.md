# Примеры кадров (живые hex-дампы)

Конкретные байты, которые вы должны видеть в UART. Подойдёт для сверки своего парсера или своего сборщика. Все CRC — реальные, посчитанные по референсной функции `DryerUart::calculateCrc()`.

!!! note
    Структуры и офсеты — [04-binary-structures.md](04-binary-structures.md). Типы и назначение — [03-message-types.md](03-message-types.md).

## Heartbeat (MCU → LINK)

**Параметры:** uptime 12 сек, поле `wifiRssiDbm` = 450 (прошивка пишет туда температуру MCU × 10 = 45.0 °C), ошибок 0, `cloudState` = 0 (в этом направлении поле не используется).

```
Offset       Hex bytes               Описание
──────────── ───────────────────────  ───────────────────────────
0x00         AA                      SOF
0x01         01                      VER
0x02         00                      FLAGS = 0
0x03         40                      KIND = Heartbeat
0x04         05                      SEQ = 5
0x05         09                      LEN = 9

0x06..0x09   0C 00 00 00             uptimeSeconds = 12
0x0A..0x0B   C2 01                   wifiRssiDbm = 0x01C2 = 450
0x0C..0x0D   00 00                   errorsSinceBoot = 0
0x0E         00                      cloudState = 0

0x0F..0x10   E7 53                   CRC16 = 0x53E7 (LE)
```

Полный кадр: `AA 01 00 40 05 09 0C 00 00 00 C2 01 00 00 00 E7 53`.

**Параметры:** Start в режиме Drying, unit 0 (U1), target = 55.0 °C, duration = 120 мин.

```

──────────── ───────────────────────────────────────────  ─────────────────────────────
0x00         AA                                         SOF
0x01         01                                         VER
0x02         01                                         FLAGS = FLAG_ACK_REQUIRED
0x03         20                                         KIND = Command
0x04         0A                                         SEQ = 10
0x05         0D                                         LEN = 13

0x06         01                                         command = Start
0x07         01                                         targetState = DryerMode::Drying
0x08         00                                         unitId = 0
0x09..0x0A   00 00                                      reserved[2]

0x0F..0x12   78 00 00 00                                arg1 = 120 (минуты)
```

## CommandAck (MCU → LINK)

**Параметры:** подтверждение Command с SEQ=10, статус OK.

```
Offset       Hex bytes        Описание
──────────── ────────────────  ──────────────────────
0x00         AA               SOF
0x01         01               VER
0x02         02               FLAGS = FLAG_IS_ACK
0x03         21               KIND = CommandAck
0x04         0A               SEQ = 10 (номер подтверждаемого Command)
0x05         02               LEN = 2

0x06         0A               ackSequence = 10
0x07         00               status = None (OK)

0x08..0x09   6F 5E            CRC16 = 0x5E6F (LE)
```

Полный кадр: `AA 01 02 21 0A 02 0A 00 6F 5E`.

## ClaimStart (MCU → LINK, пустой payload)

**Параметры:** запрос начала привязки. Payload отсутствует.

```
Offset       Hex bytes        Описание
──────────── ────────────────  ──────────────────────
0x00         AA               SOF
0x01         01               VER
0x02         01               FLAGS = FLAG_ACK_REQUIRED
0x03         70               KIND = ClaimStart
0x04         03               SEQ = 3
0x05         00               LEN = 0

0x06..0x07   84 38            CRC16 = 0x3884 (LE)
```

Полный кадр (8 байт): `AA 01 01 70 03 00 84 38`.

Это самый короткий возможный кадр в протоколе (нулевой payload + заголовок + CRC).

## Status (MCU → LINK)

**Параметры:** 1 камера, режим Drying, sessionNum = 42, target = 55.0 °C, duration = 120 мин, elapsed = 360 с, totalRemaining = 6840 с. Uptime устройства = 3600 с.

```
Full frame (141 bytes):
AA 01 00 13 0E 85 01 00 01 2A 00 00 00 26 02 00
00 78 00 68 01 00 00 00 00 00 00 00 00 00 00 B8
1A 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 10 0E 00 00 1C 6D
```

**CRC = 0x6D1C.** Разбор:

- `0x00..0x05` — заголовок: `AA 01 00 13 0E 85` (KIND=0x13, SEQ=14, LEN=133).
- `0x06` — `count = 1`.
- `0x07..0x26` — `StatusEntry[0]` (32 байта): `unitId=0, mode=Drying(1), session=42 (0x2A), targetTemp=550 (0x0226), durationMin=120 (0x0078), elapsed=360 (0x00000168), stageElapsed=0, stageRem=0, totalRem=6840 (0x00001AB8), stage fields = 0`.
- `0x27..0x86` — `StatusEntry[1..3]` нулевые (count=1).
- `0x87..0x8A` — `uptime = 3600 (0x00000E10)`.
- `0x8B..0x8C` — `CRC = 0x6D1C` (LE).

## Command с ProfilePayload (LINK → MCU, 64 байта)

Тот же `MessageKind = 0x20`, но **длина payload = 64** вместо 13 — это сигнал, что внутри `ProfilePayload`, а не `CommandPayload`.

**Параметры:** unit 0, 2 этапа:

- Этап 1: 60.0 °C, ramp = 300 с, hold = 1800 с.
- Этап 2: 100.0 °C, ramp = 600 с, hold = 6000 с.

```
Full frame (72 bytes):
AA 01 01 20 0B 40 00 02 00 00 58 02 2C 01 08 07
E8 03 58 02 70 17 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 95 0D
```

**CRC = 0x0D95.** Разбор:

- `0x00..0x05` — заголовок: `AA 01 01 20 0B 40` (FLAGS=ACK_REQUIRED, SEQ=11, LEN=**64** → ProfilePayload).
- `0x06..0x09` — `unitId=0, totalStages=2, startStage=0, _pad=0`.
- `0x0A..0x0F` — stage[0]: `temp=600 (0x0258), ramp=300 (0x012C), hold=1800 (0x0708)`.
- `0x10..0x15` — stage[1]: `temp=1000 (0x03E8), ramp=600 (0x0258), hold=6000 (0x1770)`.
- `0x16..0x45` — stage[2..9] нулевые.
- `0x46..0x47` — CRC.

Если получатель видит `kind == 0x20, len == 13` — это обычный `CommandPayload`. Если `len == 64` — это профиль.

## ConfigPush: фрагментированный конфиг (первый чанк)

Передача JSON-конфига размером 300 байт (пример). Это **первый из двух** фрагментов, несёт байты 0..193 и заголовок с `totalSize`.

```
Full frame (208 bytes):
AA 01 09 30 15 C8 34 12 2C 01 00 00 7B 22 76 22
3A 38 2C 22 75 6E 69 74 73 22 3A 33 2C 22 61 63
74 69 76 65 22 3A 30 2C 22 6C 61 6E 67 22 3A 22
65 6E 22 2C 22 6D 65 6E 75 22 3A 5B 7B 22 69 64
22 3A 33 2C 22 74 22 3A 22 76 61 6C 22 2C 22 76
61 6C 22 3A 5B 35 30 2C 36 35 2C 38 35 5D 7D 2C
7B 22 69 64 22 3A 35 2C 22 74 22 3A 22 76 61 6C
22 2C 22 76 61 6C 22 3A 5B 34 30 2C 31 35 5D 7D
2C 7B 22 69 64 22 3A 31 37 2C 22 74 22 3A 22 76
61 6C 22 2C 22 76 61 6C 22 3A 5B 35 35 2C 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 CE 97
```

**CRC = 0x97CE.** Разбор:

- `0x00..0x05` — заголовок: `AA 01 09 30 15 C8`.
  - `FLAGS = 0x09 = FLAG_ACK_REQUIRED | FLAG_FRAGMENTED` (ждём ACK, и это не последний фрагмент).
  - `KIND = 0x30` (ConfigPush), `SEQ = 21`, `LEN = 200` (максимум).
- `0x06..0x07` — `transferId = 0x1234` (LE).
- `0x08..0x09` — `totalSize = 300` (LE; в первом фрагменте заполняется).
- `0x0A..0x0B` — `chunkIndex = 0` (LE).
- `0x0C..0xCD` — `data[194]`: байты 0..193 JSON-а.
- `0xCE..0xCF` — CRC.

Второй фрагмент будет иметь `FLAGS = FLAG_ACK_REQUIRED | FLAG_LAST_FRAGMENT`, `chunkIndex = 1`, `totalSize = 0` (в последующих чанках не заполняется), и `LEN` = остаток JSON + 6 байт заголовка чанка.

**Параметры:** severity `"error"`, source `"HEATER"`, event `"OVER_MAX"`, message `"Heater over max temperature"`, unit 0.

```
Full frame (172 bytes):
AA 01 00 60 20 A4 65 72 72 6F 72 00 00 00 00 00
48 45 41 54 45 52 00 00 00 00 00 00 00 00 00 00
00 00 00 00 4F 56 45 52 5F 4D 41 58 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 48 65 61 74 65 72 20 6F 76 65 72 20
6D 61 78 20 74 65 6D 70 65 72 61 74 75 72 65 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 00 00 00 00 00 00 4D C9
```

**CRC = 0xC94D.** Разбор:

- `0x00..0x05` — заголовок: `AA 01 00 60 20 A4` (KIND=0x60, SEQ=32, LEN=164).
- `0x06..0x0F` — `severity[10]`: `"error\0\0\0\0\0"` — ASCII + нулевой хвост.
- `0x10..0x23` — `source[20]`: `"HEATER\0…"`.
- `0x24..0x43` — `event[32]`: `"OVER_MAX\0…"`.
- `0x44..0xA7` — `message[100]`: `"Heater over max temperature\0…"`.
- `0xA8` — `unitId = 0`.
- `0xA9` — `_pad = 0`.
- `0xAA..0xAB` — CRC.

## Error: CrcMismatch

**Параметры:** отправитель получил кадр с битым CRC. Битый кадр имел SEQ = 42.

```
Offset       Hex bytes              Описание
──────────── ──────────────────────  ───────────────────────────
0x00         AA                     SOF
0x01         01                     VER
0x02         04                     FLAGS = FLAG_ERROR
0x03         50                     KIND = Error
0x04         00                     SEQ = 0 (наш новый кадр)
0x05         04                     LEN = 4

0x06         01                     code = CrcMismatch
0x07         2A                     lastSequence = 42 (виновник)
0x08..0x09   00 00                  detail = 0

0x0A..0x0B   AD 18                  CRC16 = 0x18AD (LE)
```

Полный кадр: `AA 01 04 50 00 04 01 2A 00 00 AD 18`.

Обратите внимание: `FLAG_ERROR` стоит в заголовке не потому, что «этот кадр пришёл с ошибкой», а потому, что «этот кадр несёт ErrorPayload». Это явно помечает диагностический трафик.

## Проверка собственным парсером

Возьмите любой из полных дампов выше. Подайте в своём коде:

1. Прогоните все байты до CRC через функцию `crc16()` (формула в [02-frame-and-crc.md](02-frame-and-crc.md)).
2. Сравните с указанным CRC. Должно сойтись бит в бит.
3. Парсер — проверка всех offset-ов по таблице.
4. Проверьте `payloadLength` на соответствие ожидаемой длине для данного `kind` (см. [03-message-types.md](03-message-types.md)).

Если какой-то из контрольных CRC не сходится у вас — ошибка почти наверняка в одном из:

- перепутан порядок байтов (вы пишете big-endian вместо little-endian);
- начальное значение CRC не `0xFFFF` (возможно, `0x0000` или другой вариант CCITT);
- в расчёт CRC не включили заголовок, только payload.
