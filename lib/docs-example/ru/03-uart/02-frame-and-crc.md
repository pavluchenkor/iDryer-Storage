# Структура UART-кадра и CRC

Единица обмена по UART — **кадр** (frame). Эта страница — исчерпывающий справочник: что из чего состоит, какие поля обязательны, как считать контрольную сумму.

!!! note "Источник правды"
    Определения — `src/uart/uart_protocol.h`, реализация CRC — `src/uart/uart_protocol.cpp`. Всё, что ниже, сверено с этими файлами.

!!! warning "Базовые концепты — см. prerequisites"
    Дальше активно используются: фиксированные типы (`uint8_t`, `uint16_t`), **little-endian**, битовые операции (`<<`, `&`, `|`), `#pragma pack(1)`, `enum class`. Если хотя бы один пункт — «не уверен», сначала пройдите [../01-overview/05-prerequisites.md](../01-overview/05-prerequisites.md). Без этого разделы ниже будут читаться как шифр.

---

## Общий вид кадра

```
┌─────┬─────┬──────┬──────┬─────┬─────┬─────────────┬──────────────────────┐
│ SOF │ VER │FLAGS │ KIND │ SEQ │ LEN │   PAYLOAD   │ CRC16 (2B, LE)       │
│ 1B  │ 1B  │  1B  │  1B  │ 1B  │ 1B  │ 0–200 байт  │ младший байт первым  │
└─────┴─────┴──────┴──────┴─────┴─────┴─────────────┴──────────────────────┘
◄─────────── 6 байт заголовка ────────────►
```

**«LE» = little-endian**, порядок байтов «младший первым». Одинаково для **всех** многобайтовых полей в протоколе (не только для CRC). Подробнее — [prerequisites §3](../01-overview/05-prerequisites.md).

**Полная длина кадра:** `6 + LEN + 2` байт, от 8 (пустой payload) до 208 (максимум 200 payload).

## Заголовок (6 байт)

| Offset | Size | Поле | Значение | Константа |
|--------|------|------|----------|-----------|
| 0 | 1 | `sof` | Всегда `0xAA` — стартовый байт | `DryerUart::SOF` |
| 1 | 1 | `version` | Всегда `0x01` | `DryerUart::PROTOCOL_VERSION` |
| 2 | 1 | `flags` | Битовые флаги (см. ниже) | — |
| 3 | 1 | `kind` | Тип сообщения (MessageKind) | `enum class MessageKind` |
| 4 | 1 | `sequence` | Счётчик 0–255, инкремент при каждом кадре | — |
| 5 | 1 | `payloadLength` | Длина payload, 0–200 | `MAX_PAYLOAD_SIZE = 200` |

### Флаги (байт 2)

| Бит | Маска | Константа | Описание |
|-----|-------|-----------|----------|
| 0 | `0x01` | `FLAG_ACK_REQUIRED` | Отправитель ждёт ACK |
| 1 | `0x02` | `FLAG_IS_ACK` | Этот кадр — сам ACK |
| 2 | `0x04` | `FLAG_ERROR` | Payload содержит `ErrorPayload` |
| 3 | `0x08` | `FLAG_FRAGMENTED` | Промежуточный фрагмент (не последний) |
| 4 | `0x10` | `FLAG_LAST_FRAGMENT` | Последний фрагмент (для неделимых кадров — одиночный) |

Флаги могут комбинироваться. Например, ACK-ответ на фрагмент — `FLAG_IS_ACK | FLAG_LAST_FRAGMENT`.

### `sequence`

Инкрементируется у **отправителя** при каждом уходящем кадре, включая ACK. Переполняется после 255 → 0.

В кадре ACK (`FLAG_IS_ACK` = 1) поле `sequence` равно **номеру подтверждаемого кадра**, а не своему собственному. Это позволяет получателю матчить ACK с исходным запросом.

### `payloadLength`

Длина полезной нагрузки в байтах. Для каждого типа сообщения есть **ожидаемая** длина — получатель проверяет её и при несовпадении отвечает `Error{InvalidPayload}`. Единственное исключение — `Command` (`0x20`), который допускает два размера: 13 байт (`CommandPayload`) и 64 байта (`ProfilePayload`).

## Payload (0–200 байт)

Структура зависит от `kind`. Полный справочник по всем структурам: [04-binary-structures.md](04-binary-structures.md).

**Общее правило:** все структуры упакованы `#pragma pack(1)` — никакого выравнивания, байты идут подряд. Все многобайтовые числа — **little-endian**.

## CRC16-CCITT

### Параметры

| Параметр | Значение |
|----------|----------|
| Полином | `0x1021` |
| Начальное значение | `0xFFFF` |
| Reflect Input | нет |
| Reflect Output | нет |
| Xor Output | `0x0000` |
| **Стандартное имя** | **CRC-16/CCITT-FALSE** (он же CRC-16/IBM-3740) |

!!! warning "Не путайте с XMODEM"
    Онлайн-калькуляторы и библиотеки часто предлагают несколько CCITT-вариантов. У XMODEM **init = `0x0000`**, у нас **init = `0xFFFF`**. Проверяйте init.

### От каких байт считается

CRC считается от **всего заголовка и всего payload**, то есть `HEADER_SIZE + payloadLength = 6 + LEN` байт. **Не включает** сам CRC.

### Запись в кадр

CRC записывается в **два байта** после payload в **little-endian**: младший байт первым.

```
... payload[LEN-1] | (crc & 0xFF) | ((crc >> 8) & 0xFF)
```

### Реализация на C

Эта функция 1-в-1 совпадает с `DryerUart::calculateCrc()` (`src/uart/uart_protocol.cpp`):

```cpp
uint16_t crc16(const uint8_t *data, size_t len) {
    uint16_t crc = 0xFFFF;                          // стартовое значение (init)
    for (size_t i = 0; i < len; i++) {
        crc ^= (uint16_t)data[i] << 8;              // положили текущий байт в старшую
                                                    // половину 16-битного слова и XOR
        for (uint8_t bit = 0; bit < 8; bit++) {
            if (crc & 0x8000)                       // старший бит = 1?
                crc = (crc << 1) ^ 0x1021;          // да — сдвиг влево + XOR с полиномом
            else
                crc <<= 1;                          // нет — просто сдвиг влево
        }
    }
    return crc;
}
```

**Что делает код (на пальцах для новичков):**

- `0xFFFF` — «все 16 бит в единицах», начальное состояние.
- `<<= 8` — сдвиг на 8 бит (помещаем байт в старшую половину).
- `& 0x8000` — маска «старший бит 16-битного числа» (0b1000_0000_0000_0000).
- `^` (XOR) — поразрядное исключающее ИЛИ.
- Полином `0x1021` = CCITT-стандарт, не менять.

Деталь «почему именно такая последовательность сдвигов и XOR-ов» — это и есть **определение** CRC-16/CCITT. Достаточно просто скопировать функцию как есть — она работает. Если интересна теория, гуглите «CRC polynomial long division».

### Проверочные значения

На пустом массиве (len=0): `0xFFFF`.

Для контрольного кадра Telemetry из квикстарта (35 байт = заголовок 6 + payload 29, **без** двух байт CRC): **`0xDA10`**.

Для контрольного кадра Hello (92 байта = заголовок 6 + payload 86, **без** двух байт CRC): **`0xE274`**.

Полные дампы этих кадров байт-в-байт — в [06-examples.md](06-examples.md). Если написали свою функцию — прогоните её на этих данных, сравните. Совпало → CRC работает.

## Жизненный цикл кадра

### Отправитель

1. Сформировать заголовок: `sof = 0xAA`, `version = 1`, `flags` по ситуации, `kind` = тип, `sequence` = следующий номер, `payloadLength` = размер payload.
2. Сформировать payload (структура по типу).
3. Посчитать CRC от `header + payload` (6 + LEN байт).
4. Записать в UART: `header (6) + payload (LEN) + CRC_lo + CRC_hi`.
5. Если `FLAG_ACK_REQUIRED` — сохранить кадр в «pending», ждать ACK 700 мс; не пришёл — retry (до 3 раз), см. [05-ack-retry.md](05-ack-retry.md).

### Получатель

1. Ждать `0xAA` в потоке байт.
2. Прочитать 6 байт заголовка.
3. Валидировать `version == 1`, `payloadLength <= 200`. Иначе — ошибка, парсер сбрасывается.
4. Прочитать `payloadLength` байт payload.
5. Прочитать 2 байта CRC (LE).
6. Посчитать CRC от `header + payload` своим расчётом. Сравнить с полученным.
7. Если не совпал — `Error{CrcMismatch}` + сброс парсера.
8. Если совпал — `validateLength(kind, payloadLength)`. Не совпала длина для этого типа — `Error{InvalidPayload}`.
9. Если `FLAG_ACK_REQUIRED` — немедленно ответить соответствующим ACK-кадром.
10. Передать payload в handler по типу сообщения.

Референсная реализация: `DryerUart::UartBridge::processIncomingByte()` в `src/uart/uart_bridge.cpp`.

## Ограничения

- **Payload > 200 байт** — принципиально невозможно в одном кадре. Для больших JSON (конфиг меню, ~3 КБ) используется фрагментация: тип `ConfigPush` (`0x30`) с флагом `FLAG_FRAGMENTED` на промежуточных и `FLAG_LAST_FRAGMENT` на последнем. Подробно: [05-ack-retry.md](05-ack-retry.md) и [04-binary-structures.md#configchunkpayload](04-binary-structures.md).
- **RFID-данные** (888 байт) — тоже фрагментируются (`RfidReadData`/`RfidWriteData`), формат отличается: у каждого фрагмента единый заголовок `RfidDataPayload`. См. [../07-features/01-rfid.md](../07-features/01-rfid.md).
