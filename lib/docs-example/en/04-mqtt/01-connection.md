# MQTT: Connection and authorization

Everything you need for LINK to connect successfully to the iDryer MQTT broker: connection parameters, credentials, LWT, and subscriptions.

!!! note "Source of truth"
    `src/mqtt/mqtt_client.cpp` (`connect()`), `src/mqtt/idryer_topics.h` (constants), `src/mqtt/root_ca.h` (CA certificate). Terms - [../01-overview/04-glossary.md](../01-overview/04-glossary.md).

---

## Broker

| Parameter | Value |
|----------|----------|
| Production host | configured by the environment (not stored in the library repository) |
| TLS port | **8883** |
| Plain TCP port | **1883** - may be blocked by a firewall in production |
| Protocol | MQTT 3.1.1 |
| Broker | EMQX |
| Keepalive | **60 seconds** (`IDRYER_MQTT_KEEPALIVE` in `mqtt_client.h`) |
| Clean session | **false** (persistent session on the broker) |
| Max packet size | **16384 bytes** (`MQTT_BUFFER_SIZE`) - enough for `config` at about 3 KB |
| Auto-reconnect | built into `MqttClient::loop()` (through `CloudStateMachine`) |

!!! warning "Clean session: never `true`"
    The device must connect with `clean_session = false` (persistent session, `c0` in MQTT 3.1.1).

    **Why this is critical:** with `clean_session = true`, the broker deletes the `idryer/<serial>/commands/#` subscription on every CONNECT. The device then gets one chance to send SUBSCRIBE successfully. If SUBSCRIBE does not arrive on time (WiFi lag, PubSubClient buffer overflow, half-closed TCP), there is no subscription, portal commands are silently **not delivered**, and device publishes still work. This has already happened in production - see commit `a75ebc9` in `idryer-protocol`.

    In `MqttClient::connect()`, the flag is `static constexpr bool kMqttCleanSession = false;` with a strong warning. Do not change it.

    A healthy firmware in the Mosquitto log looks like this:
    ```
    New client connected ... as <serial> (p2, c0, k60, ...)
                                           ^^^
                                          c0 = clean_session=false
    ```
    If you see `c1`, the device is running a buggy firmware.

In production, **TLS** is expected. For local development and testing, plain 1883 is acceptable. Build flag: `MQTT_USE_TLS`.

### TLS

The CA certificate is the Let's Encrypt root, embedded in the firmware (`src/mqtt/root_ca.h`). HTTPS is implemented with `WiFiClientSecure::setCACert(ROOT_CA_LETSENCRYPT)`. `setInsecure()` is **not** used.

If you move the firmware to another infrastructure with a different certificate authority, replace the contents of `root_ca.h` with your root certificate in PEM format.

## Credentials

| Parameter | Value | Source |
|----------|----------|----------|
| Client ID | `serialNumber` | generated by LINK on first boot (MAC or mcuSerial), stored in NVS |
| Username | `serialNumber` | matches the Client ID |
| Password | `deviceToken` | issued by the portal in response to `POST /devices/provision`, stored in NVS |

### Broker-side verification

EMQX calls the backend HTTP auth hook (`MqttAuthService`) and passes the `(username, password)` pair. The backend checks that a `Link` with that `serialNumber` exists and that `Link.token` matches. It allows the connection if both match.

!!! warning "What does not work"
    - **User JWT** - not valid for an MQTT device. The JWT is only needed by the app when calling `POST /devices/claim`.
    - **Shared broker password** - there is no such thing. Each device has its own `(serial, token)` pair.
    - **Service user `backend` + `MQTT_BACKEND_SECRET`** - for infrastructure only (internal publications), not for devices.

### If `deviceToken` is lost (NVS erased)

A new provision is required. If the device is already claimed to an account, the portal returns `deviceToken: null` and first requires you to unclaim the device in the app. The flow is described in [../06-flows/02-claiming-flow.md](../06-flows/02-claiming-flow.md).

## LWT (Last Will and Testament)

When LINK connects, it sends the broker a "will" message that the broker will publish if the connection drops **unexpectedly** (TCP failure, power loss).

| Parameter | Value |
|----------|----------|
| Topic | `idryer/<serialNumber>/offline` |
| QoS | 1 |
| Retain | **false** |
| Payload | `{}` |

Normal shutdown (`disconnect()`) does **not** send the LWT. That is what lets the server distinguish a clean disconnect from a device outage.

Implementation: see `mqttClient_.connect(clientId, username, password, lwtTopic, 1, false, "{}")` in `connect()`.

---

## Subscriptions

After connecting, LINK subscribes to one wildcard topic:

```
idryer/<serialNumber>/commands/#
```

QoS 1. All incoming commands - `idryer/<serial>/commands/<name>` - land here. Command name and JSON body parsing live in `CommandHandler::handleMqttCommand`. Details: [04-backend-to-device.md](04-backend-to-device.md).

---

## Command responses

MQTT commands from the cloud are **not acknowledged** with a separate MQTT message. This is an asymmetric channel:

- The user publishes to `commands/...`.
- The device processes the command and reflects the result in **periodic publications** - `status`, `telemetry`, `config/delta`.

There is no topic such as `commands/ack` or `responses/...`. The backend and app must infer that the command was applied from changes in `status` / `telemetry`. Diagnostic commands (`ping`) produce no MQTT effect at all - only a Serial log entry on the device.

## Payload size limit

`MQTT_BUFFER_SIZE = 16384` bytes is the maximum `PubSubClient` can receive/send in this library. Typical sizes:

- `info` - 500-1000 bytes.
- `telemetry` - up to 400 bytes.
- `status` - up to 600 bytes.
- `config` - up to about 3 KB, depending on menu content.
- `events` - up to 500 bytes.

If the menu is complex and the `config` JSON starts exceeding about 16 KB, you need to increase `MQTT_BUFFER_SIZE` in the build.

## Connection lifecycle

```
1. WiFi connected
2. load serialNumber + deviceToken from NVS
3. TCP + TLS handshake with broker (port 8883)
4. MQTT CONNECT:
   - Client ID = serialNumber
   - Username = serialNumber
   - Password = deviceToken
   - LWT = idryer/{serial}/offline, QoS 1, retain false, payload "{}"
5. SUBSCRIBE idryer/{serial}/commands/#, QoS 1
6. PUBLISH idryer/{serial}/info (retained), QoS 1 - once after connect
7. then periodically telemetry, status, weights, rfid, events
```

There may be pauses between steps (WiFi blipped, TCP dropped). That is normal: `CloudStateMachine::loop()` reconnects automatically.

## Key library APIs

```cpp
idryer::MqttClient mqtt;

// Connection (delegated from CloudStateMachine, usually not called manually)
mqtt.begin(...);
mqtt.setCredentials(serialNumber, deviceToken);
mqtt.connect();

// Publishing
mqtt.publishInfo(hw, fw, workTime, unitsCount, units, mcuSerial, deviceType);
mqtt.publishTelemetry(jsonDoc);
mqtt.publishStatus(jsonDoc);
mqtt.publishWeights(jsonDoc);
mqtt.publishRfid(jsonDoc);
mqtt.publishEvent(jsonDoc);

// Command handling
mqtt.setCommandCallback(onMqttCommand);
```

Method details are in `src/mqtt/mqtt_client.h`.
